2. **_Data_** **_Integration_**

FPLAir's drone operations generate and use various types of data that need careful management to ensure missions are safe and effective. While FPLAir currently uses Percepto's drone-in-a-box solution, API documentation may not be immediately available. This proposed architecture is informed by experiences with similar platforms like Skydio, DJI, and Autel, as well as integration platforms like FlytBase and DroneDeploy.

Our strategy focuses on managing both real-time operational data and long-term storage needs. By separating these concerns, we can optimize each data path for its specific requirements while keeping the system cohesive.

# **Our Architecture and Approach**

Our architecture handles four main types of data: real-time telemetry for drone control, streaming media for visual feedback, geospatial data for navigation and planning, and archival data for compliance and analysis. Each type has unique needs for latency, reliability, and storage.

We use a mix of proven technologies, each chosen to meet specific data handling needs. Real-time components focus on low latency and reliability, while storage systems balance accessibility with cost-effectiveness.

## **Data Types[​](http://localhost:3000/docs/rfp/response/solution/data-integration#data-types)**

Telemetry data provides continuous updates about the drone's position, orientation, speed, and system health. This real-time information lets operators control the drone and monitor its status during flight. It also includes battery levels, signal strength, and system diagnostics, helping operators decide when to continue, modify, or end a mission. Additionally, telemetry data from the Drone Dock adds another layer of operational insight.

Video streams from drone cameras serve multiple functions during operations. The primary video feed supplies the visual information needed for navigation and inspection tasks. Secondary feeds, such as thermal imaging or alternative camera views, facilitate detailed asset inspections and enhanced situational awareness throughout the mission. These video streams also serve as an auditable record of the inspection process.

Stored media includes photos and high-resolution video files captured on-board the drone during flight. These files are typically saved locally on the drone and can be uploaded to the ground station either during flight (if bandwidth permits) or upon landing in the Drone Dock. Once transferred, they are made available for long-term storage, review, and analysis.

Environmental data reflects conditions that affect flight safety and mission success. This includes weather conditions, visibility levels, and airspace status. Operators use this data during mission planning and monitor real-time updates during flight, enabling them to adapt to changing conditions.

Mission data outlines each flight's objectives, including flight plans, waypoints, geofences, and operational boundaries. It also captures the results and observations from the mission, creating a complete record of the operation's planning and execution.

Geospatial data depicts the physical terrain and infrastructure where missions occur. This includes terrain features, locations of critical infrastructure, and other geographic information, which assist operators in planning safe and efficient routes. To support rapid visualization of this data in the Vision Pro application, a dedicated tile server caches and serves map tiles, ensuring smooth and scalable display of geographic information.

Control signals are the commands sent from operators to the aircraft. They direct drone movements, camera operations, and sensor activities. High reliability and low latency for these signals are essential, particularly in manual operations or emergency adjustments.

Operational data consists of mission-critical procedures and system status reports, including pre-flight checklists and ongoing alerts. This type of data ensures every mission adheres to established safety protocols and regulatory requirements, and includes details about the remote pilot in command.

## **Technical Architecture[​](http://localhost:3000/docs/rfp/response/solution/data-integration#technical-architecture)**

Our technical architecture balances the need for real-time performance with reliable data storage and retrieval. The system must handle both high-frequency telemetry data and large media files while maintaining responsiveness for operators and providing robust data access for post-mission analysis.

While FPLAir currently uses Percepto's platform, our architecture is designed to be vendor-agnostic, allowing for potential future transitions to other drone-in-a-box solutions. We plan to implement this architecture using proven, scalable technologies that work together to meet these diverse requirements.

We plan to use PostgreSQL as the primary system of record, chosen for its proven reliability and extensive ecosystem. PostGIS will manage geospatial information, supporting geospatial data visualization and analysis, while TimescaleDB will store historical telemetry data, allowing for efficient time-series analysis. A dedicated tile server will streamline geospatial visualization in the client application.

Redis will serve as our in-memory data store for real-time state management and caching. Redis Streams will handle the flow of real-time telemetry data from the drone platform. This data will be ingested into Redis Streams, allowing for immediate access by the Apple Vision Pro via WebSocket connections. The Vision Pro will display this data in real-time, providing operators with up-to-date information on drone status and operations.

For historical lookup, telemetry data from Redis Streams will be periodically batched and stored in TimescaleDB. This allows for efficient querying and analysis of historical flight data, supporting post-mission analysis and reporting.

For real-time video, we plan to use MPEG-TS for low-latency video streaming during active missions. MPEG-TS is a standard digital container format used for transmitting video and audio data, designed for real-time streaming applications. It offers lower latency than HLS (HTTP Live Streaming) because it streams data continuously, allowing for immediate playback as data is received, unlike HLS which segments the video stream into small parts, introducing latency. Additionally, MPEG-TS can be transmitted over UDP, which is more suitable for real-time applications due to its faster data transmission capabilities. This is essential for handling video streams.

To integrate with systems like visionOS, which cannot natively load RTMP streams, a bridge is required to convert RTMP streams from the drone platform to MPEG-TS. This conversion involves decoding the RTMP stream and re-encoding it into MPEG-TS format, ensuring compatibility and preserving low latency. We store recorded media in cloud object storage, with metadata references maintained in PostgreSQL for efficient querying and retrieval, supporting stored media.

Additionally, some of the streaming data pipeline and analytics may be developed using Python, leveraging its extensive libraries and frameworks for data processing and analysis. This approach allows for flexibility and scalability as the system evolves.

Our API layer will use Deno and GraphQL to provide a unified interface for client applications, with WebSocket solutions handling real-time telemetry and control operations, facilitating access to telemetry data and control signals.

For mapping and geospatial data, we are considering several options for tile servers, with a preference toward Cesium and Mapbox. Cesium offers strong capabilities for 3D tiles and terrain visualization, making it ideal for detailed 3D mapping. Mapbox provides excellent tools for interactive and customizable maps, supporting both 2D and 3D data. These platforms can integrate with OpenDroneMap (ODM) outputs, such as ortho stitches and 3D models, to enhance visualization capabilities.

Photogrammetry, using tools like ODM, will be incorporated into our data pipeline to create detailed ortho stitches and oblique 3D models of work areas. Other photogrammetry options include Pix4D and Agisoft Metashape, which can also be used to generate high-quality 3D models and maps. These models can be rendered in the Vision Pro as a "tabletop" visualization, providing an immersive view of the operational environment. For the MVP, this feature will be demonstrated in a controlled environment to showcase its potential.

**IV. Future Considerations (Post MVP)**

1. **_Scalability_**

Our solution will be architected to support the demands of FPLAir's centralized drone operations, designed to manage multiple high-bandwidth data streams from up to 30 drones simultaneously. By prioritizing adaptive data stream management, intelligent routing, and efficient processing across distributed resources, we can ensure a responsive, scalable platform that meets real-time operational requirements.

# **Our Architecture and Approach**

Our architecture is built to handle the complexities of scaling drone operations. It supports multiple concurrent missions, real-time data processing, and comprehensive fleet management. We focus on optimizing both real-time operations and long-term data storage to maintain system performance and reliability.

## **Key Considerations[​](http://localhost:3000/docs/rfp/response/future-considerations/scalability#key-considerations)**

**Stream Management and Data Channels:** Efficient handling of real-time telemetry, video feeds, and command data is crucial for drone operations scalability. We propose using a flexible message broker like RabbitMQ for telemetry and command data to ensure reliable message delivery, alongside a high-performance in-memory database like Redis for temporary caching of time-sensitive data. For high-bandwidth video feeds, each drone will have a dedicated media channel, allowing concurrent, seamless data processing. Edge hardware with embedded GPUs at the drone dock could preprocess video streams, compressing and filtering data before forwarding to centralized services, reducing central server load and minimizing latency.

**Horizontal Scaling and Media Channel Distribution:** To ensure robust horizontal scaling, services will be containerized and deployed across nodes that can dynamically adjust based on demand fluctuations. Beyond standard Kubernetes orchestration, we'll establish policies to handle media channel load, enabling each channel to scale independently. Edge hardware deployments at drone docks will preprocess and aggregate data streams, including telemetry and media, before central distribution, reducing network dependency and ensuring central systems handle only essential processing.

**Intelligent Routing and Data Prioritization:** For efficient and low-latency data routing from drones, we'll implement an intelligent routing layer that prioritizes critical telemetry and video data based on type, urgency, and available bandwidth. Quality of Service (QoS) settings will help maintain low-latency performance by assigning priority to telemetry, video, and control data as needed, supporting real-time mission control.

**Wireless Network Optimization:** Since the Apple Vision Pro supports only Wi-Fi, our network infrastructure will be optimized for Wi-Fi 6 on dedicated channels. This high-bandwidth, low-latency standard enables efficient handling of multiple real-time data streams, critical for uninterrupted video and telemetry feeds. Establishing dedicated Wi-Fi 6 networks for Vision Pro devices will ensure minimized interference and high-performance streaming.

**Efficient Data Processing:** Real-time data processing will be managed through a stream processing framework tailored to low-latency environments. We'll employ efficient serialization formats, such as Protocol Buffers, for telemetry and command data to reduce message size and improve transmission speeds. For video data, compression and adaptive bitrate streaming will ensure video quality dynamically adjusts to network conditions.

# **Our Architecture and Approach**

Our architecture focuses on creating a flexible and scalable platform abstraction layer that supports multiple drone platforms. This layer will standardize interactions, allowing for easy integration and management of diverse drone systems.

## **Key Considerations[​](http://localhost:3000/docs/rfp/response/future-considerations/platform-abstraction#key-considerations)**

Adapter Interfaces and Protocol Translators: We will implement a series of adapter interfaces and protocol translators to bridge the gap between our standardized command interface and vendor-specific APIs. This ensures that our system can communicate effectively with different drone platforms, translating standard control inputs into vendor-specific commands.

Telemetry Data Normalization: Telemetry data will be normalized through a common data model, ensuring consistent data handling across platforms. This includes standardizing position, orientation, speed updates, battery levels, system health metrics, and signal strength indicators.

Control Command Translation: Our command abstraction layer will translate standard control inputs into vendor-specific commands. This includes basic flight controls, navigation commands, camera and payload operations, and emergency procedures, ensuring consistent operation across different platforms.

Mission Planning Adapters: We will implement adapters for various mission planning formats, supporting standard formats like KML, KMZ, and JSON. This allows operators to use familiar planning tools while ensuring compatibility with different drone platforms.

Vendor-Specific Safety Features: While maintaining a common interface, we will incorporate platform-specific safety features, ensuring that each drone platform's unique capabilities are leveraged effectively.

GraphQL API for Abstraction: Utilizing a GraphQL API can significantly enhance our platform abstraction by providing a flexible and efficient way to query and manipulate data. GraphQL allows clients to request exactly the data they need, reducing over-fetching and under-fetching of data. This is particularly useful in a multi-platform environment where different drone systems may have varying data requirements. By abstracting the data layer with GraphQL, we can offer a unified API that adapts to the specific needs of each client application, simplifying integration and improving performance.

4. **_Other Considerations NextEra might be interested in_**

The following ideas will require much more exploration, but our team is excited about these possibilities as the technology landscape evolves

**3D Video Visualization with Depth Inference:**

With advancements in depth-mapping technology, a future direction could involve generating 3D visualizations from 2D video by inferring depth maps using tools like DepthAnything. While true 3D cameras are an option, depth mapping could be applied to standard 2D footage, providing 3D scene perception and adding valuable depth cues for operators reviewing footage post-mission. As the technology progresses, real-time depth inference could become a viable enhancement, delivering 3D video feeds during active missions. This approach would require advanced processing capabilities but could offer a cost-effective, immersive alternative to 3D cameras, supporting precise spatial assessments in complex inspection or surveillance tasks.

**Custom Gesture Controls for Enhanced Drone Operation:**

Future updates could explore leveraging visionOS’s custom gesture capabilities to provide a refined, intuitive control scheme for operators. A potential workflow might allow operators to control the drone’s movement directions (forward, backward, lateral) with their left hand, while managing ascent/descent and finer positioning with subtle adjustments. Simultaneously, the right hand could control gimbal pitch and yaw, providing flexible, real-time adjustments to both drone and camera positions. Although promising, the implementation of these custom gestures would require robust testing to ensure reliability and prevent unintentional commands, making this a longer-term development goal that could greatly enhance user flexibility once refined.

**3D Mission Waypoints and Altitude Planning with Spatial Interactions:**

For future mission planning, a spatial interface could allow operators to manage waypoints in 3D, directly adjusting altitude and positioning in mid-air. By pinching and dragging the drone icon on a 3D map, operators could set waypoints more intuitively, visually adjusting altitude within a spatial context. This interaction would contrast with current waypoint tools like DJI FlightHub or FlytBase, which rely on keyboard and mouse inputs to change altitude views. Using resources like Google’s 3D Tiles, we could eventually simulate real-world environments on a tabletop map, providing context through detailed terrain and structure visualization. This approach would make spatial mission planning more intuitive but requires advanced 3D data integration and real-time responsiveness, positioning it as a valuable but future-focused addition to the platform.

**Mission Auditing (‘Black Box’ recorder)**

With a centralized command and control system, it would be possible to record all signals and data that are used during a mission so that they could be accurately reconstructed later. This would allow both auditing and investigation in case of a critical failure, but also facilitate operator training and feedback.
